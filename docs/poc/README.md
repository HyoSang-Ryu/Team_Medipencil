# MediPencil — 출국 전 PoC 제작·사용 검증 계획

문서 ID: MP-PK-POC-001 · 작성일: 2026-10-03 · 결정: D-11

**지금의 목표는 최종 제품 구현이 아니라, 온라인 지원팀이 직접 사용하고 피드백할 수 있는 작동 PoC다.**

사용자 지시: “가기전에 먼저 poc해서 실증한후 피드백 받아서 그때 다시 명세를 만들자.”

| 구분 | 현재 상태 |
| --- | --- |
| 작업 순서 | PoC 제작 → 온라인 지원팀 사용 검증 → 피드백·재시험 → 명세 재작성·사용자 승인 |
| PoC 구현 | READY_FOR_CODEX. 이번 문서 변경에서 앱을 제작·배포한 것은 아님 |
| 사용·기술 검증 | NOT_RUN. 실행 결과나 참여자의 피드백을 아직 수집하지 않음 |
| 후속 상세명세 | AFTER_FEEDBACK. 지금 다시 전체 DB/API를 확정하지 않음 |
| 대회 사전제작·반입·재사용 허용 | UNCONFIRMED. 내부 PoC 제작 요청과 별개이며 자동 승인하지 않음 |

## 2026-10-04 추가 요청: 팀 코멘트와 디자인 적용 안내

사용자 요청에 따라 PoC 모드 직원 메뉴에 팀 코멘트 저장/조회 기능을 추가한다. 기존 협업 도구만 사용하던 지침에 대한 제한적 변경이며, 채팅·회의·첨부·알림 플랫폼 확장은 아니다. 실제 의견 원문은 저장소 밖 회차 DB에 남기고 공개 가능한 요약만 등록부로 옮긴다. 코멘트가 저장됐다는 사실만으로 실제 사용 검증·조치 확정을 선언하지 않는다.

디자인 작업 전달에는 [UI/UX 디자인 적용 안내](ui-design-handoff.md)를 사용한다. 실제 사용법과 검증 결과는 [검토 안내](review-guide.md), [검증 로그](validation-log.md)를 따른다. 아래 최초 계획의 READY/NOT_RUN 상태는 문서 작성 당시 기준이다.

## 1. 기존 문서를 어떻게 사용할 것인가

D-11은 개발 순서와 현재 명세의 적용 방식을 바꾸는 결정이다. v1.1을 승인했던 사실이나 이전 작성 이력을 지우지 않는다.

- [제품 설계 v1.1](../design/medipencil-final-design-v1.1.md): 문제 정의, 5단계 돌봄 루프, 화면의 참고 기준. 근거·승인·권한 원칙은 유지한다.
- [기존 상세명세 01~03](../development/README.md): 검증 전 가설·설계 후보 및 추적 기준. 18개 테이블, 40개 API, C-01~C-12 전체를 지금 그대로 구현하는 요구가 아니다.
- 현 단계에서는 **이 문서와 루트 AGENTS.md가 PoC 작업 순서·범위의 우선 기준**이다. 이전 PREPARATION/P/C 규정은 대회용 구현 작업에 남으며, 내부 PoC 작업은 아래 PC 단계로 별도 관리한다. 이 구분은 행사 규정의 예외를 뜻하지 않는다.
- PoC에서 얻은 사실을 바탕으로 채택·수정·보류·삭제할 요구사항을 정하고, 사용자 승인 후에 다음 명세를 만든다.

대조한 이전 저장소 기준: `9c64133960f8305c0dab9e3713009bbb39e46e1c`. 이 기준의 main에는 문서·SVG가 있었고 앱 소스는 없었다. 다른 브랜치나 로컬 개발 상태는 Codex가 작업 시작 시 다시 확인한다.

## 2. 이번 PoC에서 확인할 다섯 가지

| 검증 질문 | 실제로 확인할 것 |
| --- | --- |
| 흐름을 이해하는가 | 가족 질문이 어디로 가고, 누가 확인하며, 언제 답이 돌아오는지 지원팀이 설명할 수 있는가 |
| 서로 다른 사용자가 연결되는가 | 한 브라우저의 질문이 서버·DB에 저장되고 다른 직원 세션에서 보이며, 승인·발행 후 가족 세션에 반영되는가 |
| 내용이 믿을 만한가 | 예정과 완료, 진술과 관찰, 원문과 설명을 구분하는가. 문장과 출처의 의미가 맞는가 |
| 잘못된 공개를 막는가 | 승인 전 노출, 다른 입주자의 기록, 동의 없는 정보, 철회 후 재조회가 차단되는가 |
| 실제 엔진을 붙일 수 있는가 | 사용권·접근권이 확인된 STT/LLM의 처리시간·오류·수정 부담은 어떤가. 미연결이면 무엇이 아직 검증되지 않았는가 |

여기서 실증은 **독립 합성자료를 사용한 내부 기능·사용성·기술 검증**이다. 실제 환자·입주자 대상 임상시험이나 실제 돌봄 업무 절감의 입증으로 표현하지 않는다.

## 3. 작동 PoC의 최소 범위

가족 상황판 → 질문 등록 → 직원 질문 큐 → 대화/텍스트 입력 → 기록 초안 수정·승인 → 발행 → 가족의 답·근거 확인을 실제 서버와 저장소를 통해 연결한다. 화면은 1~5의 역할을 담되, 검증에 불필요한 화면 분리는 강제하지 않는다.

| 실제 구현 | 축소하거나 뒤로 미룰 것 |
| --- | --- |
| 가족·직원별 별도 세션, 같은 합성 입주자/질문 ID의 연결, 재접속 후 저장 내용 조회 | 상용 회원가입·조직관리·의료기관 연동 |
| 실제 질문 저장, 담당·확인 예정·미답변 유지, 수정·승인·발행의 구분 | 전체 업무배정·자동 임상 우선순위 |
| 원문 근거 확인, 오전 계획과 오후 실행 확인을 구별한 기록 | 복잡한 검색·벡터DB·자체 모델 학습 |
| 두 가족의 서로 다른 공개 범위, 동의 후보와 확인·철회, 서버 측 응답 제한 | 정식 전자서명·법률 동의 체계 완결 |
| 직접 입력으로 먼저 전 과정을 연결하고, 확인된 엔진은 교체 가능한 연결부로 추가 | 미확인 외부 API·엔진을 필수 의존성으로 두는 것 |
| 오류·미확인·모의 처리 표시, 반복 시연 초기화, 최소 진행/검증 기록 | 2.1 사전문진·예약·푸시·전체 다국어·스트리밍 |

화면 이동만 되는 목업이나 완성 답변을 하드코딩한 화면을 동작 PoC로 보고하지 않는다. 고정 합성 입력과 모의 AI 결과는 개발 점검에 사용할 수 있으나 **SIMULATED/REPLAY**로 표시하고 실추론과 구분한다. 직접 입력 경로 통과는 AI 성능 검증 통과가 아니다.

기본 개발 조합은 기존 후보인 FastAPI/Python + SQLite + React/TypeScript/Vite를 활용한다. 구현자가 실제로 필요한 최소 구조를 선택하고 간단한 이유를 기록한다. 물리 테이블·API 개수 맞추기에 시간을 쓰지 않는다. 단, 승인·식별키·근거·권한의 불변 조건은 간소화하지 않는다.

한국 원격 검토자가 이해할 수 있는 한국어 설명/문구를 먼저 제공하고, 핀란드어 검토가 필요한 핵심 문구를 별도 표시한다. 핀란드어 성능은 핀란드어 시험과 검수 없이 통과로 처리하지 않는다.

## 4. Codex 작업 순서

| 작업 | 산출물·완료 기준 |
| --- | --- |
| PC-00 출발점 기록 | HEAD·branch·작업 트리·기존 코드·자산을 확인. 기존 작업을 보존하고 PoC 작업 브랜치를 사용. 이 문서의 범위·미결 조건을 작업 기록에 남김 |
| PC-01 첫 작동 루프 | 독립 합성자료와 직접 입력으로 가족 질문부터 발행·열람까지 구현. 서로 다른 브라우저 세션과 DB에서 실제 연결 확인 |
| PC-02 오류·공개 경계 | 근거 없는 추가 내용, 승인 전 노출, 계획→완료 오인, 수신자별 권한, 철회·저장 실패·중복 요청을 시험. 안전상 결함을 먼저 수정 |
| PC-03 실제 엔진 시험 | 확인된 엔진만 연결하고 합성 입력의 처리시간·실패·수정량 기록. 권리·접근·비용 조건이 없으면 해당 시험만 BLOCKED로 남기고 사용자 검토는 계속 |
| PC-04 온라인 검토 | 승인된 공유 환경에서 지원팀이 직접 사용. 동일 build·시나리오의 결과와 자유 사용 의견을 기록. 서버 미지정이면 로컬 완료까지만 보고하고 공유 배포는 대기 |
| PC-05 수정·재검증 | 필수 수정과 개선 제안을 구분해 작은 수정 반복. 수정 전후와 같은 사례의 재시험을 기록 |
| PC-06 피드백 종합 | 검증된 기능·실패·미검증·남은 질문을 정리하고 명세 재작성에 필요한 결정안을 사용자에게 제출 |

과거 C 작업을 자동으로 모두 실행하지 않는다. 새 전체 명세 작성으로 PC-01을 지연하지 않는다. 사소한 코드 수정마다 재승인을 받지 않되, 범위 확대·유료 사용·모델 다운로드·새 외부 전송·서버 배포·데이터 삭제는 해당 권한과 대상을 확인한다.

구현은 `poc/remote-validation` 같은 별도 작업 브랜치에 작은 커밋으로 남긴다. 기존 커밋·작성 시점을 보존하고, 대회용 코드로 자동 병합하거나 행사 중 새로 작성했다고 표시하지 않는다. 브랜치 분리는 변경·기여 추적 장치이며 규정 면제 장치가 아니다.

## 5. 온라인 지원팀과 검토하는 방법

지원팀은 PoC 검토자다. 대회 정식 참가자·주최 측 멘토로 자동 간주하지 않는다. 이름·역할·기여 범위의 관리와 대회 기여 허용 여부는 구분한다.

**1차는 같이 보고, 2차는 직접 사용한다.** 같은 시나리오를 설명한 뒤 검토자가 별도 브라우저에서 가족 역할과 직원 역할로 수행한다. 최소 두 개의 독립 세션이 필요하며, 검토 인원과 담당은 팀에서 정한다. 지원팀을 대신해 피드백을 작성하지 않는다.

| 검토 사례 | 관찰할 결과 |
| --- | --- |
| 정상 연결 | 가족이 질문하고 직원이 답을 확인·승인·발행한 뒤 가족에게 돌아오는 과정과 이해도 |
| 기록/답변 부족 | 오후 확인 기록 없이 산책 완료가 뜨지 않는지, 미답변 질문이 남는지 |
| 다른 수신자·철회 | Liisa/Mikko의 답과 출처 범위가 다른지, 동의 후보는 권한을 바꾸지 않는지, 철회 후 신규 접근 제한 |
| 처리 실패 | 입력·STT·저장·발행 실패에서 기록과 질문을 잃지 않는지, 재시도가 중복을 만들지 않는지 |
| 엔진 사용 | 실제 provider와 모의 경로를 구분하고 생성·검토·수정 시간을 따로 측정하는지 |

반드시 적을 의견: 막힌 화면/동작, 예상한 결과, 실제 결과, 재현 순서, 개선 이유. ‘좋다/별로다’만 남기지 않는다. 원격 검토 결과는 실제 시설 실무자의 검증과 구별한다.

공유 환경은 팀이 승인한 테스트 서버·접근 경로를 사용한다. 미인증 역할 전환을 인터넷에 그대로 노출하지 않는다. 최소한 검토자 접근 제한, HTTPS 또는 승인된 VPN, 서버 측 역할 구분, 테스트 회차/사용자 데이터 분리, reset 권한 제한이 필요하다. 비밀 URL이나 robots 설정만으로 접근 통제를 대체하지 않는다. DB·음성·피드백 원본은 공개 GitHub에 올리지 않는다.

서버 주소·배포 권한·인증수단이 아직 정해지지 않았다. Codex는 없는 접속주소를 보고하거나 임의로 운영서버를 수정하지 않는다. 일반 협업 도구/회의 기록으로 피드백을 수집하며 별도 채팅·회의 플랫폼을 새로 개발하지 않는다.

## 6. 측정·증빙과 통과 판정

코드 단위 시험, 브라우저 간 연동 시험, 실제 AI 시험, 사람 사용성 검토를 별도 칸에 기록한다. 실제 모델이 없으면 AI 검증은 NOT_RUN/BLOCKED다. 임의로 ‘정확도 100%’나 ‘업무시간 0’ 같은 수치를 채우지 않는다.

최소 측정은 질문~답변 흐름의 성공/실패, 대기·생성·사람 검토·수정 시간, 근거 없는 추가 문구의 건수/시험 수, 공개 차단의 성공/실패, 미답변·실패 후 복구 결과다. 표본 수, 모의/실제 provider, 환경, 회차를 함께 적는다. 작은 내부 시험을 임상 성능·현장 효과로 일반화하지 않는다.

Codex는 실제 작업을 시작할 때 `docs/poc/validation-log.md`를 만들고 다음 형식으로 관리한다. 현재 그 파일이나 실제 결과가 존재한다고 가정하지 않는다.

```text
실행: 회차 | build commit | 환경 | 시나리오 | 검토자 역할/익명 ID
모드: 직접 입력 / SIMULATED / 실제 STT·LLM / REPLAY
결과: PASS / FAIL / NOT_RUN / BLOCKED
측정: 실제 시간·건수·표본 수 | 원본 증빙의 내부 위치
피드백: FB-ID | 화면/동작 | 재현 순서 | 예상/실제 | 영향 | 제안
조치: 유지/수정/보류/제외 | 담당 | 수정 commit | 재시험 결과
```

원문·음성·실제 이름·연락처·비공개 회신·검토자 개인정보는 공개 로그에 적지 않는다. 공개 가능한 익명 요약과 비공개 증빙의 식별자만 남긴다. 저장된 시연 결과를 실시간 처리로 표시하지 않는다.

**PoC 완료**는 직접 작동하는 루프, 핵심 안전 시험, 실제 지원팀 피드백, 중요 결함 재시험이 확인된 상태다. AI 시험 등 남은 항목은 명시한다. 지원팀 피드백이 아직 없으면 ‘검토 준비 완료’까지만 보고한다. 화면만 있거나 자동 테스트만 통과한 상태를 ‘실증 완료’로 처리하지 않는다.

## 7. 피드백 이후에 다시 만들 명세

PC-06에서 먼저 `유지할 요구 / 변경할 요구 / 불필요한 요구 / 아직 확인할 요구`를 사용자에게 제시한다. 합의 후 실제 화면, 상태 흐름, 필요한 데이터 구조/API, 엔진 연결, 배포·보안, 시험 기준을 다시 명세한다.

반영표는 `FB-ID → 확인된 문제 → 결정 → 변경할 명세 절 → 수정/재시험 증빙`으로 연결한다. v1.1과 개발명세 v1.0은 역사적 기준으로 보존하고, 다음 버전 번호·확정일·승인자는 실제 승인 시 기록한다. 지금은 다음 명세를 자동 확정하지 않는다.

## 8. 대회 규정과 별개로 남는 결정

2026-10-03 공식 행사 페이지에 연결된 참가규정 Versio 3(버전 날짜 2026-09-24)의 §5·§7·§8을 확인했다. §7은 환경·범용 부품·기존 제품·접근방법 준비를 허용하지만 과제에 특화된 해결책은 행사 중 제작하도록 한다. 별도 시행일이나 **내부 PoC이므로 예외**라는 조항은 확인되지 않았다.

**이 PoC가 출품 과제와 같은 기능을 사전에 구현하므로, 내부 검토 목적·합성자료·별도 브랜치·제출 제외 표기만으로 사전제작 또는 참가 적격성 문제가 해소되지 않는다.** 사용자 지시는 내부 개발 업무에 대한 요청이지 주최 측 허가가 아니다. 대회용 재사용·출품은 미확정으로 유지하고, 제작 전 허용 범위를 확인하는 것이 가장 안전하다. 이미 제작했다면 실제 범위·시점·기여를 숨기지 않고 확인받는다.

주최 측 확인 질문은 두 가지다. (1) 온라인 지원팀과 사용성을 검토하기 위한 과제 관련 작동 PoC를 사전에 만들고 그 범위·작성 이력을 신고하는 경우, 제작·반입·재사용과 출전 자격을 어떻게 적용하는가? (2) 등록된 팀원 외 지원 인력이 검토·코딩·시험에 참여하는 각각의 허용 범위는 무엇인가? 팀 인원 규정만으로 모든 외부 피드백이 금지됐다고 단정하지 않는다.

현재 PoC 입력은 Veil.AI에서 유래하지 않은 독립 합성자료만 사용한다. Veil 자료·실제 환자·입주자 기록·실제 돌봄 음성은 사용하지 않는다. 실제 provider 사용권·비용·전송·보관 조건은 별도로 확인한다.

- 공식 행사 페이지: https://www.luvn.fi/fi/sote-ai-hackathon-2026
- 연결된 참가규정: https://admin.luvn.fi/sites/default/files/2026-09/SOTE%20AI%20Hackathon%202026_S%C3%A4%C3%A4nn%C3%B6t%20ja%20osallistumisehdot.pdf

주최 측 회신은 아직 받지 않았다. 이번 저장소 변경은 회신 발송·수신, 행사 규정 완화, 실제 앱 구현·공유 배포의 증빙이 아니다.
