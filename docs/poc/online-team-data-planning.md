# 온라인팀 논의용 — 과제 2.2 데이터 확보·제작 계획

작성일: 2026-10-13  
목적: 1차 가족 생활 현황에 필요한 자료의 제공 여부, 부족분, 전달 형식, 역할과 검증 방법을 결정한다.  
상태: 논의 초안. 아래 담당·기간·규모는 제안이며 실제 배정이나 합의가 아니다. 음성은 2차로 제외한다.  
관련: [전체 정리](task-2-2-implementation-summary.md), [핵심 범위](family-daily-life-core-scope.md)

## 1. 이번 논의에서 결정할 것

- 센서·웨어러블 모형 데이터가 별도로 제공되는가? 파일·스키마·사용 조건은 무엇인가?
- 제공 자료가 생활 현황에 부족한 항목은 무엇이며, 누가 독립 합성자료를 제작하는가?
- 환자 식별·관찰 시각·단위·출처·누락 표현을 어떻게 통일할 것인가?
- 첫 시연의 환자 수·기간·생활 항목·필수 시나리오는 무엇인가?
- 현지팀과 온라인팀이 각각 무엇을 확인하고 언제 전달할 것인가?

현재 의료·사회복지 파일은 배경 이력 후보다. 센서 데이터가 포함됐거나 매일의 돌봄 관찰이 충분하다고 가정하지 않는다. 로컬 분석 결과는 별도 보관하며 공개 저장소·채팅·외부 AI로 원본을 복사하지 않는다.

## 3. 전달 형식 제안

네트워크 연동 전에 작은 독립 합성 JSON/JSONL 묶음으로 계약을 맞춘다. 확정 API·DB 스키마가 아니라 교환 필드 초안이다.

|필드 묶음|필요 필드·규칙|
|---|---|
|식별|event_id, subject_id, cohort_id, source_id, source_version. 키는 이름 대신 사용|
|시간|observed_at 또는 interval_start/interval_end, recorded_at, received_at. 시간대 명시; 날짜만 있으면 임의 시각을 실제 측정처럼 만들지 않음|
|내용|topic, event_type, value, unit, statement. 구조화 값과 서술문을 구분|
|출처|source_kind(sensor/staff_record/existing_record), evidence_refs, data_origin, integration_mode|
|의미|claim_type(observation/reported/estimated/plan), action_status. 센서 추정과 확인된 행위를 구분|
|품질|quality_status, missing_reason. null과 관찰된 0을 구분; 구간 미수신은 coverage/gap 정보로 표현|
|확인|review_status, reviewed_at, reviewed_by, linked_event_ids. 미검토 AI 결과를 직원 확인으로 표시하지 않음|
|정정|supersedes_event_id, version. 기존 근거를 덮어쓰지 않음|
|공유|required_scopes 및 별도 동의/수신자 정책. 센서 제공자가 보호자 권한을 결정하지 않음|

출처는 TEAM_SYNTHETIC / VEIL·VEIL_DERIVED 등 실제 계보를 보존한다. 모형 센서라고 해서 실제 기기를 실행한 것으로 표시하지 않는다. 값의 단위 변환·시간대 변환은 원본과 변환 규칙을 남긴다.

## 4. 첫 데이터 묶음 제안

규모 제안: 가상 입소자 2명, 최근 7일로 첫 통합 시험 후 30일로 확장. 두 부모를 조회하는 보호자와 권한이 다른 보호자 사례는 격리 테스트용으로 구성하고 현재 공개 계정에 자동 추가하지 않는다.

|시나리오|입력 구성|기대 결과|
|---|---|---|
|일상적인 하루|식사·움직임·활동 관찰과 자료 시각|확인된 사실의 쉬운 생활 요약|
|움직임 감소·사유 미확인|비교 가능한 두 기간의 모형 신호|감소 사실과 사유 미확인 표시; 질병/기분 추정 없음|
|직원 확인 후 갱신|이전 사건을 참조한 확인 기록|확인된 설명과 조치만 안내에 추가|
|침대 점유와 수면 추정 차이|서로 다른 종류의 이벤트|점유 시간을 숙면으로 표현하지 않음|
|활동 예정·실제 참여|계획만 있는 경우와 후속 관찰이 있는 경우|실행 확인 전후를 구분|
|약통 열림·복용 미확인|기기 신호만 제공|복용 완료 문구 차단|
|누락·지연·오래된 기록|비어 있는 구간과 늦게 도착한 이벤트|0으로 채우지 않고 최신성·갱신 상태 표시|
|출처 간 충돌|같은 대상/시간의 상충 관찰|임의 결론 대신 직원 확인 대상으로 연결|
|동의 철회·정정·중복|수신자 정책 변경과 기존 사건의 수정/재전송|이전 공개 무효화·비공개 숨김·중복 방지|

한 사람이 매일 모든 항목을 완벽하게 기록한 자료만 만들지 않는다. 결측은 실패가 아니라 시험할 정보 상태다. 변화 판정 기준은 현장과 논의하고 임의의 의료 위험 판정으로 확대하지 않는다.

## 5. 역할 분담 제안

기존 사용자 지정 원칙: 현지팀은 현지 요구 확인·핀란드어 검수·화면/API/AI 구현·합성데이터 관리, 온라인팀은 그 외 지원. 공통팀의 기존 역할은 유지한다. 아래는 데이터 업무의 구체화 제안이며 담당자 이름은 미정이다.

|업무|현지팀|온라인팀|공동 확인|
|---|---|---|---|
|제공 자료 확보|담당자에게 센서 제공 여부·사용 조건·필드 의미 확인|필요 자료 요청 목록·스키마 체크리스트 준비|자료 사용/공유 가능 범위|
|독립 합성자료|시나리오·내용 생성과 버전 관리 주관|형식 검사·누락/충돌/중복 시험 사례 제안|정상/실패 사례 범위|
|화면/API/AI 적용|구현과 로컬 연동 주관|검증 도구·테스트 입력/기대 결과 지원|데이터 계약과 변경 통지|
|요약 정답|현장 의미·핀란드어 검수|근거 추적·회귀검사 구성|허용 사실·금지 해석|
|인수 검증|업무 흐름과 표현 확인|키/시간/단위/품질/권한 검사 결과 정리|미해결 사항과 다음 회차|

## 6. 온라인팀에 논의할 질문

- 센서 파일/명세를 현지팀이 언제 확인할 수 있는가? 미제공 시 독립 합성 시연으로 진행할 것인가?
- 첫 시연을 2명·7일로 시작해 30일로 확장할 것인가?
- 움직임 지표는 감지 횟수·활동 시간·걸음수 중 무엇인가? 비교 가능한 정의가 있는가?
- 침대 데이터와 수면 추정 데이터는 별개인가? 야간 구간과 날짜는 어떻게 표현되는가?
- 식사·산책·취미·사회적 참여를 뒷받침하는 기록이 있는가? 부족분 제작 담당과 검수자는 누구인가?
- 비교 기준과 ‘직원 확인 필요’ 조건은 무엇인가? 의료 위험 판정과 어떻게 구분할 것인가?
- 지연/오프라인일 때 마지막 유효 자료를 어떻게 표시하고 언제 숨길 것인가?
- 개발·검수·공유 환경별로 허용되는 데이터 계보는 무엇인가?
- 자동검증 항목과 현지 의미 검수 항목을 누가 언제 인수할 것인가?

## 7. 인수 체크리스트

- [ ] 출처·사용 조건·보관/공유 범위를 문서화했다.
- [ ] 모형 데이터와 실제 센서 실행을 구분했다.
- [ ] 코호트와 환자 키가 충돌하지 않고 다른 환자 결합이 없다.
- [ ] 값·단위·시각·관찰 구간·시간대가 명확하다.
- [ ] 신호·추정·관찰·계획·직원 확인을 구분했다.
- [ ] 0/미확인/미수신/해당 없음을 구분했다.
- [ ] 원문 근거와 정정 이력을 추적할 수 있다.
- [ ] 보호자별 공개·철회·중복 전달 실패 사례가 있다.
- [ ] 문장별 허용 사실·금지 해석·기대 질문이 정리됐다.
- [ ] 핀란드어 검수 결과와 미검수 항목을 구분했다.
- [ ] 파일 버전·생성 방법·검사 결과·알려진 한계를 함께 전달했다.
